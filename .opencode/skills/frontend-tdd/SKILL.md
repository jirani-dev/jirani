# Frontend TDD

Use this skill when implementing behavior on the `frontend/` side of the monorepo: a new React component, hook, route, design-token surface, or end-to-end flow. Stay inside the superpowers `test-driven-development` skill for the discipline itself (red-green-refactor, characterization first on legacy code, never delete a failing test, write the failing test first for every bugfix) — this skill only carries the frontend runner, toolchain, and MCP choices. If the change is mainly about design quality (palette, type scale, layout principles, "avoiding AI slop" defaults), pair this skill with the vendored Anthropic `frontend-design` skill rather than overriding it; `frontend-design` is the authority on aesthetics.

The unit and integration loop runs on vitest. During development use `vitest` (watch mode) for fast feedback; on the gate run `vitest run` exactly as recorded in `frontend/package.json` — read the file first, never invent a script name. Colocate `*.test.ts` and `*.test.tsx` next to the unit they cover so the file tree mirrors the source. Until vitest is installed locally (deferred per the 2026-09-15 frontend opencode-setup handoff), the gate reduces to `npm run lint` and `npx tsc --noEmit`; in that interim, the skill tells the agent to file the first failing test (and colocate it), ask the human before running `npm install vitest --save-dev` (the frontend DoD treats `package.json` and `package-lock.json` as generated, and the `review` agent enforces the no-hand-edit rule), then add the `test` script to `package.json` (ask again — same constraint), then enter the real red-green loop. Never hand-roll a vitest API you have not seen in `node_modules/vitest` or in the vitest docs; when in doubt, fetch through context7.

The e2e loop runs through the Playwright and Chrome DevTools MCPs, both wired under `mcp` in `.opencode/opencode.jsonc`. Use the Playwright MCP to drive: navigate, click, fill forms, assert against the accessibility tree (no vision model needed), and mock the network with `browser_route` when the backend is unavailable. When a test fails or behavior looks wrong, switch to the Chrome DevTools MCP for inspection: source-mapped console stacks, network requests, Lighthouse audits, performance traces (LCP/CLS/FCP), and V8 heap snapshots. The division of labor — Playwright drives, Chrome DevTools debugs — is fixed; do not mix them. Chrome DevTools is Chrome stable only; if Firefox or WebKit coverage is needed for a specific bug, fall back to the Playwright MCP's built-in browser support rather than adding a separate debug layer.

Prefer Playwright Test Agents for generating new e2e tests: `npx playwright init-agents --loop=opencode` scaffolds a planner/generator/healer triplet that opens with the documented pattern and stays inside it. Hand-rolling a raw `playwright.sync_api` script is a fallback for one-off exploratory scripts, not the default path for new committed tests; for raw Playwright usage, treat the vendored Anthropic `webapp-testing` skill as the reference (it ships its own `scripts/with_server.py` and `examples/`).

The only thing this skill must not do is duplicate process. Process questions — what to do first, whether a test is "really" failing, when to characterize before refactoring, when not to delete a test — belong to the `test-driven-development` skill and stay there.

Read these first: `docs/devs/specs/react-kickoff-annex.md` (the frozen backend contract — response shapes may gain fields, never lose or rename them; API calls go through same-origin nginx `/api/*`), `frontend/package.json` (current scripts and dependencies), `frontend/eslint.config.js` (lint rules), and `frontend/tsconfig.app.json` (TS strict settings — no `any` in new code).
